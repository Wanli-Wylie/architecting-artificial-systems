# An X-Road instance and its governing authority

X-Road is software and a set of standards for exchanging data between organizations. An X-Road instance is the system built from it under one governing authority. The Estonian instance, X-tee, is run by the Information System Authority (RIA). Since 2018 the English name X-Road refers to the technology that Estonia, Finland and Iceland develop through the Nordic Institute for Interoperability Solutions (NIIS), and X-tee names the Estonian instance. RIA describes X-tee as "a technological and organizational environment enabling a secure Internet-based data exchange between information systems", and says it is "mostly focused on managing the Estonian X-tee ecosystem". The NIIS terms define an instance the same way, as "a legal, organizational and technical environment" that is "limited to the participants administered by one governing authority".

The case studies that instance. The agencies and companies that join are its members and its clients, and their information systems and registries lie outside it. Finland's instance is another governance, reached by agreement.

## What the governing authority holds

The instance puts a few things in one place and leaves the rest with the members. The NIIS terms define the governing authority as the authority "that sets the requirements for using X-road and establishing the procedure for using X-Road, managing and regulating participants of X-Road". In Estonia a Government regulation on the data exchange layer, issued under the Public Information Act, names RIA as the centre responsible for managing and developing X-tee. It lists the centre's tasks, among them keeping the information on members, registered security servers and subsystems, processing applications for membership, subsystems and security servers, setting the conditions for joining and use and publishing them, monitoring use, handling security incidents, and restricting a member's rights in the cases the regulation sets out. The regulation also requires members to carry out the orders the centre sends them. Read with the centre's tasks, these orders are the governance at work: they enforce the conditions of membership, as in a security incident or a breach of the regulation, and do not hand a member part of the centre's own work.

Admission is a transaction between the applicant and RIA. An applicant applies, concludes a joining agreement with the centre that fixes rights, obligations and responsibility, and may be refused on grounds the regulation lists, for example that the applicant has no unique identifier for which an e-seal certificate meeting the published requirements can be issued. The centre may end a membership at once, or restrict it, when a member breaches the regulation, the joining agreement or the member's rules for intermediating services.

The central server carries the part of this that the security servers need at run time. It "manages the database of X-Road members and security servers" and holds "the security policy of the X-Road instance": the trusted certification authorities, the trusted time-stamping authorities and "tunable parameters such as maximum allowed lifetime of an OCSP response". The member database and the policy together form the global configuration. The central server signs it, and security servers download and cache it. The terms call it "a technical solution, through which X-Road governing authority regulates participants of X-Road". Some parameters are the governing authority's to set. The OCSP lifetime "is defined by the owner of the central server and can vary between different instances of X-Road", and so is the longest permitted gap between logging a message and time-stamping it. The architecture says the governing authority "installs and maintains central server and central security server". The central server's own management services are offered as ordinary X-Road services through that security server.

The security policy is policy in the vocabulary's sense. It settles which authorities the verification mechanism accepts and with what parameters, and it can change, or differ between instances, without changing that mechanism. The regulation fixes the kinds of trust service a member must use for its e-seal: a qualified certificate, certificate validity confirmation and time-stamping, as in eIDAS. It treats an e-seal as valid if validity confirmation and time stamp are no more than eight hours apart, and it forbids a member to process exchanged data that cannot be confirmed by such a seal.

## Members, roles and the exchange

Members exchange data through their own security servers. The architecture states the design as "the data exchange happens directly between organizations. There are no intermediaries", and "X-Road does not change ownership of data. The data owner (service provider) controls who can access particular services." The security server's main function is "to mediate requests between a service client and a service provider", and the provider's security server "applies access control to incoming messages, thus ensuring that only those users that have signed an appropriate agreement with the service provider can access the data". The core therefore authenticates and authorizes organizations: "X-Road core handles authentication and access control on the organization level. End-user authentication is performed by information system of the service client." Every regular message is kept with its signatures in the security server's message log, whose purpose is "to provide means to prove the reception of a request/response message to a third party". Time-stamping of the log is asynchronous, and security servers stop forwarding messages if it has been failing for some time.

Service client and service provider are roles the standard defines, and the instance gives them authority. The standard says there are "no predetermined roles": once admitted, "it can act as both service client and service provider without having to perform any additional registration." The terms define a service client as a member, subsystem or access rights group "that has access rights to one or more services", and a data service provider as the member responsible for provision, "incl. granting the service SLA, managing the agreements with dataservice clients, granting access rights etc." The Estonian regulation uses its own words (data service provider, user and intermediary, the last a member that gives people outside its organization access through its system). It requires that a service be used and provided under an agreement between the two members that fixes the security measures, any permission to intermediate, and service levels, and that only a registered subsystem with an access right can use a service. Authority thus comes from two places: the centre admits the member and registers its subsystems, and the provider grants each client's access under an agreement. Neither is a delegation. The centre does not hand a member part of its own work, and a provider does not act for a client.

Horizontally, then, the exchange is request and service under agreement among members, with the governing authority supplying admission, the common protocol and the trust policy. Vertically, the instance has the governing authority above the members, and a member has structure of its own: it ensures the authentication and authorization of its end users, and an access rights group can have its administration delegated to a group administrator. No delegation structure spans the members.

## What it shows

The record of data stays with its owner. The population register is where an address is authoritative, and any other member asks for it. X-Road gives the join between members its own meaning and owner: signed, time-stamped, logged calls under an agreement, with the central server holding information about participation and nothing about citizens. RIA puts the principle this way: "the owner controls the data throughout the whole process, and the X-Road technology only offers a secure data exchange."

Availability is partly chosen in the mechanism. Security servers cache the global configuration and "continue to be fully operational while the cached global configuration remains valid", but an out-of-date copy "forbids security servers from processing incoming requests", so the validity period bounds how long the central server can be down. OCSP works the same way: when cached responses cannot be refreshed the servers cannot communicate, and their lifetime bounds the outage. Time-stamping is decoupled from exchange to keep a time-stamping authority's outage from stopping traffic, at the cost of a bounded period of messages without a time stamp. The records are evidence of what the exchange carried, not of the effect in the provider's system, which only the provider can confirm. That limit is a judgment from the log's stated purpose.

The once-only principle sits in Estonian law and policy. e-Estonia, a promotional source, says "collecting the same data in separate databases is not allowed" and that another agency "must send an electronic request to verify this information". The regulation and the architecture documents describe the exchange and its conditions of membership and do not describe a check that prevents a second copy. The principle is a requirement the architecture serves by making the request cheap and trustworthy, not one the software enforces.

## Where the vocabulary strains

The security server realizes an interface for a member's information system, which is a layer in the sense of realization, but nothing is delegated through it. Central server procedures (configuration generation, signing, refresh) are mechanisms, and the actors are the governing authority and the members.

"Source of truth" is the vocabulary's word; the sources say data owner, and the owner is the provider. The regulation's "centre", the standard's "service provider" and the Estonian "data service provider" name roles and are used as each source uses them. "Trust" in the sources is mostly about certificates, which is narrower than a trusted boundary in the vocabulary's sense.
