# Kubernetes controllers

A Kubernetes cluster is run by one organization, whose administrators decide which components run in it and who may do what through its API. The Kubernetes project is the supplier of the software and of the conventions its documentation sets out, and the people who deploy applications on the cluster, or build platforms and extensions on it, are its clients. What they rely on is that a declared intention, such as three replicas of a Pod template or a Job run to completion, keeps being pursued after it has been stated, through machine failures and through restarts of Kubernetes' own components.

## The system as its documentation describes it

The documentation compares controllers to a thermostat: "In Kubernetes, controllers are control loops that watch the state of your cluster, then make or request changes where needed. Each controller tries to move the current cluster state closer to the desired state." A controller tracks at least one resource type, and those objects have "a spec field that represents the desired state". The API conventions say the specification "is a complete description of the desired state", and that `status` "summarizes the current state of the object in the system".

Every object is reached through one API server, backed by etcd, the "Consistent and highly-available key value store for all API server data". Writers are reconciled optimistically: "Kubernetes leverages the concept of resource versions to achieve optimistic concurrency." Controllers learn of changes by watching the API, and the client-go library keeps the watched objects in a local store that a controller typically reads.

Controllers mostly act by writing more objects. "The Job controller does not run any Pods or containers itself. Instead, the Job controller tells the API server to create or remove Pods." A Deployment's controller creates ReplicaSets, which create Pods. The scheduler "Looks for Pods not yet bound to a node, and assigns each Pod to a suitable node", and the kubelet "Ensures that Pods are running, including their containers". Once a Pod is scheduled, the controller documentation says, it becomes "part of the desired state for a kubelet".

The Deployment page defines when its work is done. Kubernetes marks a Deployment complete when all its replicas have been updated to the latest version, all are available and no old replicas are running, and the Deployment controller records this as a Progressing condition in `.status.conditions`. When a rollout stalls past its progress deadline, "Kubernetes takes no action on a stalled Deployment other than to report a status condition", and the page leaves any further step to higher-level orchestrators that read it.

Burns et al. place this design among its predecessors. Unlike Omega, which exposed a shared store directly to trusted components, "state in Kubernetes is accessed exclusively through a domain-specific REST API that applies higher-level versioning, validation, semantics, and policy". The reconciliation loop "takes actions to converge the observed and desired states", and "Because all action is based on observation rather than a state diagram, reconciliation loops are robust to failures and perturbations: when a controller fails or restarts it simply picks up where it left off." They call the combination of microservices and small control loops "control through choreography", "a conscious design choice in contrast to a centralized orchestration system, which may be easier to construct at first but tends to become brittle and rigid over time". The controller documentation gives the same reason operationally: "It's useful to have simple controllers rather than one, monolithic set of control loops that are interlinked. Controllers can fail, so Kubernetes is designed to allow for that."

## Two structures among the loops

Work is handed down a chain written in objects. A user's Deployment states the task; the Deployment controller turns it into a ReplicaSet, the ReplicaSet controller into Pods, the scheduler binds each Pod to a node and the kubelet there runs it. Each step leaves room for choice (any Pod the template admits, replaced at a controlled rate) and the result comes back as status that the one above reads: observed replica counts, conditions, `observedGeneration`, which the conventions define as the generation "most recently observed by the component responsible" so that a reader can tell whether status describes the current spec. What counts as done for the whole is the Deployment page's definition of complete, computed from what is observed, so a Deployment is not done merely because its ReplicaSet reports. Ownership in Kubernetes' sense follows the same chain: "Owner references help different parts of Kubernetes avoid interfering with objects they don't control", and the Deployment page adds "Do not manage ReplicaSets owned by a Deployment."

Other relations run across the chain. The HorizontalPodAutoscaler's controller adjusts the replica count in a Deployment that a user wrote. Burns et al. describe the split: the autoscaler "simply adjusts the desired number of pods, without worrying about how those pods are created or deleted", so that it can "focus on demand" prediction. Deployments and Jobs both create Pods, and the Job controller does not delete the Pods a Deployment created because labels tell them apart. The node controller reads node heartbeats (updates to a Node's status and a Lease object per node), sets a node's Ready condition to Unknown when it becomes unreachable, and by default "waits 5 minutes between marking the node as Unknown and submitting the first eviction request", rate-limiting evictions. These loops coordinate through shared records and have no delegation between them, and neither shape is read off the other.

## How things come to be, and who may change them

Everything in the cluster that anyone cares about is an object in the API, and an object comes to be and changes only through writes to the API server. That makes the question of who may change what a question about writers, and Kubernetes answers it in several layers that work at different grains.

The coarsest is the cluster's own governance. When the controller manager runs with `--use-service-account-credentials`, the RBAC documentation says it "starts each controller using a separate service account", with a role for each built-in controller named `system:controller:...`; extensions arrive as operators, "clients of the Kubernetes API that act as controllers for a Custom Resource". Built-in controllers' roles are the project's, and the cluster's administrators bind them. RBAC says which kinds of object a controller may write at all.

Within an object the grain is finer, and several writers commonly share one object: a user writes the Deployment, the autoscaler adjusts its replicas, the Deployment controller writes its status. Server-side apply is the machinery that keeps this orderly. The API server records in `managedFields` which manager last set each field. When a different manager applies a change to a field someone else manages, that is a conflict, and the apply is refused unless it is forced; when forced, "ownership moves from its current manager to the manager making the change". So the moment of disagreement is made visible and decided on the spot, field by field, and not left to whichever write lands last. The documentation recommends that controllers force conflicts on what they manage, "since they might not be able to resolve or act on these conflicts": a person can stop and think about a conflict, and a control loop cannot, so the loop is given the standing right to take the field back. It works through a handover in which a user gives the `replicas` field to the autoscaler's controller "so they don't accidentally fight with the HorizontalPodAutoscaler (HPA) and its controller". The handover is a deliberate change of who may change the field, performed once, so that afterwards the two never contend.

Writers also hold copies. Controllers act on the objects their local stores have cached from the watch, and a copy can be old by the time a decision made on it is written back. Resource versions are how the system notices: "Kubernetes leverages the concept of resource versions to achieve optimistic concurrency", so a writer working from a stale copy finds that out when it writes and can read again, and no lock is held while it thinks. Underneath, etcd replicates the object data so that it survives machine loss, and reads come through the API server and the controllers' local stores. The Borg scheduler works the same way, from a cached copy that the master checks, and the paper compares it to Omega's optimistic concurrency ([Borg](borg.md)).

Kubernetes' own word "owner" names a different relation, between an object and its dependents, used for deletion and to keep loops off each other's objects. Field managers, owner references, labels and role bindings are four separate answers to the same worry, that two loops will act on one thing with nothing between them to settle it, each carried by the API and its records and not by a protocol among the loops.

## What it shows

Making the plan state, not a stored workflow, lets many small loops compose without a coordinator: each loop's input is an object some other loop's output has been written into, and a restarted loop re-reads and acts on the difference. The conventions say "the system's behavior is level-based rather than edge-based", and the documentation accepts that the cluster may not settle: "As long as the controllers for your cluster are running and able to make useful changes, it doesn't matter if the overall state is stable or not." The price is the conventions above that keep loops off one another's objects, and the work of getting them right for each new controller or extension.

The physical side is quietly present throughout. Loops can be small and restartable because everything they need is re-read from a replicated store, and they can be level-based because a watch can be replayed and a status can be recomputed from what is observed. Machines go quiet without announcing it, and the node controller shows how the documentation faces that: a quiet node is not assumed failed or healthy, its Ready condition becomes Unknown, and eviction waits a configurable time, so that the system waits to learn which it is.

Two descriptions the sources do not use fit loosely. "Delegation" fits the chain from Deployment to Pod with a qualification: the task travels as a written object and the result returns as status, with no coordinator between the loops, which Burns et al. call choreography, and the sources speak of control loops that create objects other loops watch, not of requests answered to a requester. And a controller is not a service others call; its interface is the API objects it watches and writes, so loops compose through those objects and not by using one another. The kubelet is called the "node agent" in its reference page, a source's term, and most of what it does is carry out Pod specs and report.
