# Kubernetes controllers

A Kubernetes cluster is run by one organization, whose administrators decide which components run in it and who may do what through its API. The Kubernetes project is the supplier of the software and of the conventions its documentation sets out, and the people who deploy applications on the cluster, or build platforms and extensions on it, are its clients. What they rely on is that a declared intention, such as three replicas of a Pod template or a Job run to completion, keeps being pursued after it has been stated, through machine failures and through restarts of Kubernetes' own components.

## The system as its documentation describes it

The documentation compares controllers to a thermostat: "In Kubernetes, controllers are control loops that watch the state of your cluster, then make or request changes where needed. Each controller tries to move the current cluster state closer to the desired state." A controller tracks at least one resource type, and those objects have "a spec field that represents the desired state". The API conventions say the specification "is a complete description of the desired state", and that `status` "summarizes the current state of the object in the system".

Every object is reached through one API server, backed by etcd, the "Consistent and highly-available key value store for all API server data". Writers are reconciled optimistically: "Kubernetes leverages the concept of resource versions to achieve optimistic concurrency." Controllers learn of changes by watching the API, and the client-go library keeps the watched objects in a local store that a controller typically reads.

Controllers mostly act by writing more objects. "The Job controller does not run any Pods or containers itself. Instead, the Job controller tells the API server to create or remove Pods." A Deployment's controller creates ReplicaSets, which create Pods. The scheduler "Looks for Pods not yet bound to a node, and assigns each Pod to a suitable node", and the kubelet "Ensures that Pods are running, including their containers". Once a Pod is scheduled, the controller documentation says, it becomes "part of the desired state for a kubelet".

The Deployment page defines when its work is done. Kubernetes marks a Deployment complete when all its replicas have been updated to the latest version, all are available and no old replicas are running, and the Deployment controller records this as a Progressing condition in `.status.conditions`. When a rollout stalls past its progress deadline, "Kubernetes takes no action on a stalled Deployment other than to report a status condition", and the page leaves any further step to higher-level orchestrators that read it.

Burns et al. place this design among its predecessors. Unlike Omega, which exposed a shared store directly to trusted components, "state in Kubernetes is accessed exclusively through a domain-specific REST API that applies higher-level versioning, validation, semantics, and policy". The reconciliation loop "takes actions to converge the observed and desired states", and "Because all action is based on observation rather than a state diagram, reconciliation loops are robust to failures and perturbations: when a controller fails or restarts it simply picks up where it left off." They call the combination of microservices and small control loops "control through choreography", "a conscious design choice in contrast to a centralized orchestration system, which may be easier to construct at first but tends to become brittle and rigid over time". The controller documentation gives the same reason operationally: "It's useful to have simple controllers rather than one, monolithic set of control loops that are interlinked. Controllers can fail, so Kubernetes is designed to allow for that."

## Two structures among the loops

Work is delegated down a chain written in objects. A user's Deployment states the task; the Deployment controller turns it into a ReplicaSet, the ReplicaSet controller into Pods, the scheduler binds each Pod to a node and the kubelet there runs it. Each step leaves latitude (any Pod the template admits, replaced at a controlled rate) and the result returns as status the delegator reads: observed replica counts, conditions, `observedGeneration`, which the conventions define as the generation "most recently observed by the component responsible" so that a reader can tell whether status describes the current spec. The composition rule is the Deployment page's definition of complete, computed from what is observed, so a Deployment is not done merely because its ReplicaSet reports. Ownership in Kubernetes' sense follows the same chain: "Owner references help different parts of Kubernetes avoid interfering with objects they don't control", and the Deployment page adds "Do not manage ReplicaSets owned by a Deployment."

Other relations run across the chain. The HorizontalPodAutoscaler's controller adjusts the replica count in a Deployment that a user wrote. Burns et al. describe the split: the autoscaler "simply adjusts the desired number of pods, without worrying about how those pods are created or deleted", so that it can "focus on demand" prediction. Deployments and Jobs both create Pods, and the Job controller does not delete the Pods a Deployment created because labels tell them apart. The node controller reads node heartbeats (updates to a Node's status and a Lease object per node), sets a node's Ready condition to Unknown when it becomes unreachable, and by default "waits 5 minutes between marking the node as Unknown and submitting the first eviction request", rate-limiting evictions. These are coordination through shared records among loops that have no delegation relation, and neither shape is read off the other.

## Authority and the source of truth

Which controller may write what is a matter for the cluster's governance. When the controller manager runs with `--use-service-account-credentials`, the RBAC documentation says it "starts each controller using a separate service account", with a role for each built-in controller named `system:controller:...`; extensions arrive as operators, "clients of the Kubernetes API that act as controllers for a Custom Resource". Built-in controllers' roles are the project's, and the cluster's administrators bind them.

The vocabulary's owner corresponds to the field manager. Under server-side apply the API server records in `managedFields` which manager last set each field, a different manager's change is a conflict unless forced, and "ownership moves from its current manager to the manager making the change". The documentation recommends that controllers force conflicts on what they manage, "since they might not be able to resolve or act on these conflicts", and it works through a handover in which a user gives the `replicas` field to the autoscaler's controller "so they don't accidentally fight with the HorizontalPodAutoscaler (HPA) and its controller". Storage is a separate matter: etcd replicates the data, reads come through the API server and the controllers' local stores, and resource versions let a writer find that its copy was stale. One object's fields may belong to several managers, so authority over the truth is per field here. Kubernetes' own "owner" is a different relation, between an object and its dependents, used for deletion and for keeping loops off each other's objects.

## What it shows, and where the vocabulary strains

Making the plan state, not a stored workflow, lets many small loops compose without a coordinator: each loop's input is an object some other loop's output has been written into, and a restarted loop re-reads and acts on the difference. The conventions say "the system's behavior is level-based rather than edge-based", and the documentation accepts that the cluster may not settle: "As long as the controllers for your cluster are running and able to make useful changes, it doesn't matter if the overall state is stable or not." The price is conventions, owner references, field managers, labels and role bindings, that keep loops off one another's objects.

"Delegation" fits the chain from Deployment to Pod with a qualification: the task travels as a written object and the result returns as status, with no coordinator between the loops, which Burns et al. call choreography. The sources speak of control loops that create objects other loops watch, not of requests answered to a requester. "Complete actor" strains: a controller's interface is the API objects it watches and writes, not an execution capability offered to others, so loops compose through shared state rather than by using one another. The kubelet is called the "node agent" in its reference page, a source's term, and most of what it does is carry out Pod specs and report. The node controller shows the kubelet's boundary as the documentation draws it: a quiet node is not assumed failed or healthy, its Ready condition becomes Unknown, and eviction waits a configurable time.
