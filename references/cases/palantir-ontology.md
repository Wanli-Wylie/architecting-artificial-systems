# Palantir Foundry Ontology

The system studied here is one organization's Foundry deployment and the Ontology inside it, a runtime description of the organization's objects, relations and actions that people, applications and programs query and act on. The organization governs it: it decides who may build types, who may submit which actions, and which source systems are connected. Palantir is the supplier of the platform, and the owners of the connected source systems are, for this design, suppliers of data and recipients of write-back. The case rests on Palantir's public documentation as of October 2026. It makes no claim about any deployment and does not endorse the product.

## The system as documented

Palantir calls the Ontology "an operational layer for the organization" that "sits on top of the digital assets integrated into the Palantir platform (datasets, virtual tables, and models)" and connects them to real-world counterparts, "ranging from physical assets like plants, equipment, and products to concepts like customer orders or financial transactions". The documentation divides it into semantic elements (objects, properties, links) and kinetic elements (actions, functions, dynamic security). An object type is "the schema definition of a real-world entity or event", an object is one instance of it, and a link type is "the schema definition of a relationship between two object types", traversable from either side. The documentation stresses that the Ontology is not "an abstract data model": it "maps each ontological concept to an organization's actual data". Objects come from backing datasources, or from actions alone when an object type has none.

An action is "a single transaction that changes the properties of one or more objects, based on a user-defined logic", and an action type is "the definition of a set of changes or edits to objects, property values, and links that a user can take at once". It carries parameters, rules and submission criteria. Rules either edit the Ontology (create, modify or delete objects, create or delete many-to-many links) or cause other effects (a notification, a webhook, a schedule build). A function rule excludes all others, "since function code alone is capable of handling everything that other rules can do". Functions are TypeScript or Python logic run server-side, with "first-class support" for "reading the properties of various object types, traversing links, and flexibly making Ontology edits". The architecture page adds that the logic behind an action could be "a simple business rule, a conventional machine learning model, an LLM-driven function, or a complex multi-step orchestration".

Submission criteria are "the conditions that determine whether an action can be submitted". They combine conditions on the submitting user (ID, group membership, attributes such as organization), on parameter values including properties of the objects passed, and on whether the action runs inside an Ontology Scenario. Each action type has its own criteria, independent of who may edit the action type, and each failure has a message shown to the user. The documentation's example is an airline letting only a flight controller change the aircraft on a flight, and only to an aircraft still in operation. The role is the organization's; the criteria give it authority over this action by naming a group. Permissions are described on two planes: object, link and action types "define the schema", while objects and links hold "actual primary key and property values". The architecture page says the security system "has to reconcile all of these granular policies, at the time of interaction", for humans and for AI-powered agents, whose scopes "either inherit from a human user, or from the permissions structure of a defined project". That is the one place the documentation passes authority from one actor to another, and it does so as a permission scope; it describes no tasks handed to agents.

## Where each fact lives

Edits show the arrangement most plainly. When an action is applied, "the data-modification logic is immediately applied to the index in the object databases and periodically flushed into a persistent store in the form of Foundry datasets owned and managed by Funnel". The Actions service sends an instruction to the Funnel service, which keeps it in a queue "that has offset tracking to support simultaneous user edits". Funnel also owns "a merged dataset that combines data coming from datasources and user edits"; indexed data in the object databases is "considered ephemeral". An object that receives data from both a datasource and user edits "must be transparently resolved with a conflict resolution strategy", configured per datasource of an object type. Under the default, "the final state of an object is always determined by the user edits applied to it" for the edited properties; the alternative applies an edit only if it is more recent than a timestamp value from the datasource. "Deletions are not considered an edit." Properties that exist only through edits always take them.

So a fact has two writers, the feed and the user's action, and a stated rule decides between them. The merged dataset is derived. Which writer's value is authoritative for a property is a choice the platform exposes per object type and datasource, and what a source system holds may differ from what the Ontology shows. Two consequences follow in the documentation. Version checks protect an action's edits: Object Storage v1 checks every object version it loaded, and v2 checks only the objects that generated edits, which the documentation says brings "weaker guarantees" and does not guarantee that "objects read outside of edit generation have not changed". And the source system must be told: actions "must be written back" through webhooks and Change Data Capture mirrors keep a low-latency copy.

## What "done" means

The webhooks page is explicit about completion. A webhook configured as writeback runs before the other rules, and if it fails "no other changes will be made", which gives "some degree of transactionality between Foundry and the external system", though "it is still possible that the external request may succeed but Ontology changes could fail". A webhook configured as a side effect runs after the edits, shows the user no failure, and "executing the side effects may happen after the success message is shown"; the documentation suggests it for "best-effort notifications". Notifications are sent once the edits have applied. A schedule rule starts its build before the edits are applied. So the commit of the Ontology edit, the external system's change and a downstream effect are distinct observations with different timing, and the action type's configuration chooses which ones a user's success message reports. The documentation gives no rule that composes them into one result beyond that choice.

## Reading it in the vocabulary

The semantic elements are a reified logical world: objects, relations, states and actions with defined meaning exist at runtime for people and programs to query and act on. Action types carry preconditions (submission criteria), effect (rules) and a unit of commit (the transaction), and the same validations apply wherever an action is submitted, in any application. "Operational layer" fits the vocabulary's layer too: applications and functions use object and action types through the Ontology's interfaces, and datasources, object databases and Funnel's merged dataset realize them beneath. Palantir also says the Ontology is not a "semantic layer", which it takes to mean a thin one; its architecture page groups dozens of components into a Language, an Engine and a Toolchain, where "the Engine substantiates every component of the Language".

The Ontology also shows a join given its own owner and contract. Many separately built systems keep their records; the platform hosts an operable logical world above them, with a second path for edits, a queue, a merge rule, a conflict strategy and write-back to maintain. A system with a single store and owner would need none of it, and the same documentation treats an object type with no datasource as ordinary.

## Where the vocabulary strains

The documentation describes no delegation among actors and no requests between them, so the case shows neither a vertical nor a horizontal structure of actors; what it shows horizontally is relations among sources and systems (feed and edit, Ontology and external system). "Actor" adds little: the documentation names operators, users and developers as those who submit actions and build on the SDK, and action types, functions and criteria are mechanisms with contracts. Whether an LLM-driven function holds a task and chooses depends on the function and is not answered. "Interface" has a Foundry meaning, "an Ontology type that describes the shape of an object type and its capabilities", giving polymorphism, which differs from the vocabulary's; it is used here only in the vocabulary's sense and marked when otherwise.
