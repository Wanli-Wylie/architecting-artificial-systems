# Palantir Foundry Ontology

The system studied here is one organization's Foundry deployment and the Ontology inside it, a runtime description of the organization's objects, relations and actions that people, applications and programs query and act on. The organization governs it: it decides who may build types, who may submit which actions, and which source systems are connected. Palantir is the supplier of the platform, and the owners of the connected source systems are, for this design, suppliers of data and recipients of write-back. The case rests on Palantir's public documentation as of October 2026.

## The system as documented

Palantir calls the Ontology "an operational layer for the organization" that "sits on top of the digital assets integrated into the Palantir platform (datasets, virtual tables, and models)" and connects them to real-world counterparts, "ranging from physical assets like plants, equipment, and products to concepts like customer orders or financial transactions". The documentation divides it into semantic elements (objects, properties, links) and kinetic elements (actions, functions, dynamic security). An object type is "the schema definition of a real-world entity or event", an object is one instance of it, and a link type is "the schema definition of a relationship between two object types", traversable from either side. The documentation stresses that the Ontology is not "an abstract data model": it "maps each ontological concept to an organization's actual data". Objects come from backing datasources, or from actions alone when an object type has none.

An action is "a single transaction that changes the properties of one or more objects, based on a user-defined logic", and an action type is "the definition of a set of changes or edits to objects, property values, and links that a user can take at once". It carries parameters, rules and submission criteria. Rules either edit the Ontology (create, modify or delete objects, create or delete many-to-many links) or cause other effects (a notification, a webhook, a schedule build). A function rule excludes all others, "since function code alone is capable of handling everything that other rules can do". Functions are TypeScript or Python logic run server-side, with "first-class support" for "reading the properties of various object types, traversing links, and flexibly making Ontology edits". The architecture page adds that the logic behind an action could be "a simple business rule, a conventional machine learning model, an LLM-driven function, or a complex multi-step orchestration".

Submission criteria are "the conditions that determine whether an action can be submitted". They combine conditions on the submitting user (ID, group membership, attributes such as organization), on parameter values including properties of the objects passed, and on whether the action runs inside an Ontology Scenario. Each action type has its own criteria, independent of who may edit the action type, and each failure has a message shown to the user. The documentation's example is an airline letting only a flight controller change the aircraft on a flight, and only to an aircraft still in operation. The role is the organization's; the criteria give it authority over this action by naming a group. Permissions are described on two planes: object, link and action types "define the schema", while objects and links hold "actual primary key and property values". The architecture page says the security system "has to reconcile all of these granular policies, at the time of interaction", for humans and for AI-powered agents, whose scopes "either inherit from a human user, or from the permissions structure of a defined project". That is the one place the documentation passes authority from one actor to another, and it does so as a permission scope; it describes no tasks handed to agents.

## How a property gets its value

A property can change in two ways. The backing datasource delivers new rows, carrying whatever the source system's own processes did under that system's owners, or a user or program applies an action, under the action type's submission criteria. The documentation follows the second path closely. When an action is applied, "the data-modification logic is immediately applied to the index in the object databases and periodically flushed into a persistent store in the form of Foundry datasets owned and managed by Funnel". The Actions service sends an instruction to the Funnel service, which keeps it in a queue "that has offset tracking to support simultaneous user edits". Funnel also owns "a merged dataset that combines data coming from datasources and user edits"; indexed data in the object databases is "considered ephemeral". An object that receives data from both a datasource and user edits "must be transparently resolved with a conflict resolution strategy", configured per datasource of an object type. Under the default, "the final state of an object is always determined by the user edits applied to it" for the edited properties; the alternative applies an edit only if it is more recent than a timestamp value from the datasource. "Deletions are not considered an edit." Properties that exist only through edits always take them.

So where both paths reach one property, a rule chosen when the object type is configured settles which change stands, and the outcome does not depend on which arrived last unless the rule says so. The index takes each edit first and serves reads, but the documentation calls it ephemeral; what lasts is Funnel's merged dataset, the result of applying that rule, and it catches up at the next flush. The rule settles what the Ontology shows and nothing else. The source system's owners go on changing their own record, and that record learns of a Foundry edit only if the action writes it back: actions "must be written back" through webhooks, and Change Data Capture mirrors keep a low-latency copy. Without write-back, one property has two values in two places, each changed by its own path, and the per-datasource rule reaches only one of them. For an object type with no datasource the situation is simpler. Its objects come to be through actions alone, and Foundry's own datasets are where they are kept.

Concurrent actions raise a different question: whether the objects an action read are still as it read them when its edits land. Object Storage v1 checks every object version it loaded, and v2 checks only the objects that generated edits, which the documentation says brings "weaker guarantees" and does not guarantee that "objects read outside of edit generation have not changed". The storage engine's check thus decides what an action's logic may assume: under v2, logic that reads one object in order to edit another can act on a value someone has since changed.

## What "done" means

The webhooks page is explicit about completion. A webhook configured as writeback runs before the other rules, and if it fails "no other changes will be made", which gives "some degree of transactionality between Foundry and the external system", though "it is still possible that the external request may succeed but Ontology changes could fail". A webhook configured as a side effect runs after the edits, shows the user no failure, and "executing the side effects may happen after the success message is shown"; the documentation suggests it for "best-effort notifications". Notifications are sent once the edits have applied. A schedule rule starts its build before the edits are applied.

The commit of the Ontology edit, the external system's change and a downstream effect are therefore three events with different timing, and the action type's configuration chooses which of them a user's success message waits for. Two separately run stores with no common commit allow little more. Ordering is the lever: calling the external system first lets its failure stop the edits, and nothing lets a failed edit undo a call that has already succeeded. The documentation gives no rule that composes the three into one result beyond that choice.

## Reading it

Palantir's name for the thing is apt. An ontology is an account of what there is, and Foundry makes part of an organization's account run: its plants, orders and flights become objects, their relationships links, and the changes people may make action types. The documentation insists on this when it says the Ontology is not "an abstract data model", and again when it says it is not a "semantic layer", which it takes to mean a thin one. Its architecture page groups dozens of components into a Language, an Engine and a Toolchain, where "the Engine substantiates every component of the Language". The Language is the account, and the Engine is what carries it out: the object databases, Funnel and its queue, the version checks, the webhooks.

Making the account run changes what kind of thing it is. A data model describes how an organization changes its records; an action type is how the change is made, and people and programs act through it. Its submission criteria are where the organization's roles take effect for that action, and its rules are what the action does. In the airline example the role of flight controller belongs to the organization and the action type names that group, while the condition on the aircraft's status turns a business rule into a precondition. The same validations apply wherever the action is submitted, in any application. Who may edit the action type is a separate permission, so the people who may change a flight's aircraft and the people who may change the rule for changing it are held apart.

The account also acquires a physical side of its own, with its own ways of failing: an index that is fast and ephemeral, a queue that orders simultaneous edits, a persistent store flushed periodically, version checks whose strength depends on the storage engine, and calls to systems it does not control. Each shapes what an action can promise. A system with a single store and owner would need little of this. The machinery is the price of hosting one operable account over many separately kept records: a second path by which properties change, a rule per datasource between the paths, a queue, and write-back to keep the other side informed. It pays where many people and programs need to act through the same objects across those records.

## Where the reading strains

The documentation describes no delegation among actors and no requests between them, so the case shows neither a vertical nor a horizontal structure of actors; what it shows horizontally is relations among sources and systems (feed and edit, Ontology and external system). Calling anyone here an actor adds little. The documentation names operators, users and developers as those who submit actions and build on the SDK, and action types, functions and criteria are mechanisms with contracts. Whether an LLM-driven function holds a task and chooses depends on the function, and the documentation does not say. Foundry's own "interface" is "an Ontology type that describes the shape of an object type and its capabilities", a means of polymorphism among object types.
